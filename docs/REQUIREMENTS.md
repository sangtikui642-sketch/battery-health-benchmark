# Battery Health Benchmark - Requirements v0.1

Status: approved for MVP development on 2026-08-27.

## 1. Product objective

Provide battery algorithm researchers with a reproducible framework for importing public
battery data, preventing cell-level data leakage, training SOH prediction baselines, and
producing traceable metrics and reports.

## 2. Approved MVP decisions

| Decision | Approved value |
|---|---|
| Primary target | SOH prediction |
| First real dataset | MATR |
| User interface | CLI only |
| Initial executable data | Synthetic fixtures |

RUL prediction, web interfaces, embedded deployment, deep learning, and cross-dataset
transfer are deferred beyond the MVP.

## 3. Users

- Battery algorithm researcher: compares models using leakage-safe evaluation.
- Repository maintainer: adds datasets and models through stable interfaces and configuration.
- Technical interviewer: understands the problem, evidence, and individual contribution quickly.

## 4. Domain definitions

For the MVP:

`SOH = current measured capacity / configured reference capacity`

The reference capacity and its provenance must be explicit in configuration or source data.
The software must not silently infer a reference capacity when neither source is available.

Minimum normalized cycle fields:

- `cell_id`: stable cell identity
- `cycle_index`: integer cycle order
- `capacity_ah`: measured discharge capacity in ampere-hours

Voltage, current, temperature, and timestamp are optional until a feature explicitly requires
them. Every normalized field must declare its unit.

## 5. Functional requirements

### FR-01 Data import

The system shall map a configured input table into the normalized cycle schema. It shall fail
without partial output when required fields are missing.

### FR-02 Data quality

The system shall report missing values, duplicate `(cell_id, cycle_index)` pairs, invalid
capacities, cell count, and cycle count. Invalid records shall not be silently discarded.

### FR-03 Leakage-safe splitting

The system shall split by `cell_id`. A cell shall occur in exactly one of train, validation, or
test. The split manifest shall record cell identifiers, random seed, and strategy.

### FR-04 SOH labels

The system shall calculate SOH from measured and reference capacity, and record the reference
capacity source. Missing reference capacity shall produce an actionable error.

### FR-05 Baseline training

The MVP shall support linear regression, random forest, and histogram gradient boosting through
a common fit/predict interface. Preprocessing shall be fitted on training data only.

### FR-06 Evaluation

The system shall report MAE, RMSE, MAPE, R-squared, test sample count, and test cell count. It
shall save per-cycle predictions and at least one actual-versus-predicted plot.

### FR-07 Reproducibility

Every run shall retain its effective configuration, split manifest, random seed, dependency
lock, and available Git revision. Repeated deterministic runs shall agree within a documented
tolerance.

### FR-08 Data protection

Repository checks shall reject credentials and disallowed raw-data locations. Tests shall use
anonymous, reproducible fixtures rather than company or personal data.

## 6. Non-functional requirements

| NFR-07 | Failure transparency | Negative results are retained and labeled |

| NFR-09 | Usability | Demo requires no more than three documented commands |
| NFR-10 | Continuous checks | Tests, lint, formatting, and types are automated |

## 7. MVP acceptance criteria

1. Synthetic data completes import, split, training, and evaluation through the CLI.
2. A MATR adapter is validated against a legally usable representative sample.
3. Three baseline models use the same saved split manifest.
4. An intentionally leaking split is rejected by an automated test.
5. Metrics and plots are generated by recorded commands rather than manual editing.
6. The suite contains at least 20 tests with zero skipped and zero xfailed tests.
7. A fresh environment can follow the README to reproduce the demo.
8. Repository scans find no private data, credentials, or absolute local paths.
9. Reports state both findings and limitations.
10. The maintainer can explain the data flow, split policy, and model interfaces.

## 9. Definition of done for one behavior

1. The Gherkin scenario is reviewed and linked to a requirement ID.
2. An executable acceptance test demonstrates the expected failure.
3. The smallest implementation makes that scenario pass.
4. Unit tests cover relevant edge cases.
5. Full regression, Ruff, formatting, and mypy checks pass.
6. Documentation reflects the implemented behavior without overstating evidence.
